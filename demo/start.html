Install it, and watch it hold a commit.

Seven steps, about twenty minutes, nothing but a shell. Every command and every line of output below was captured from a real run — the installer from the published release, the rest from the binary it installed. If any of it does not reproduce on your machine, that is our problem, not yours.

What this is: a record an agent cannot fake, and a gate it has to ask. What it is not: a sandbox, a permission system, or anything that decides on its own what is safe.

1. Install it

curl -fsSLO https://github.com/dmitrypehovski/mint/releases/latest/download/install.sh less install.sh bash install.sh

  checksum a907b61b8c91cf0e47583614ec497dffb30c6792b222d2e06e55fc14c44872ab matches
  installed mint 0.2.2 — A receipt proves that this record was issued by the holder of the stated key and has not been altered since. It does not prove the action was correct, that its inputs were true, that a person approved it, or that the world changed the way the record describes.
  note: /tmp/start-demo-home/.local/bin is not on your PATH — add it, or set MINT_BIN=/tmp/start-demo-home/.local/bin/mint

No Rust, no cargo, no clone. The installer checks the download against the checksums published with the release, and installs nothing that does not match.

2. Ask it about a command that changes something

mint guard --command "git commit -m 'first change'" --receipts .mint2
  write   hold   — this step commits something and no approval bound to it was presented
  decided by mint.policy/0.1 v1, rules a8bed408510ec43a
  the action is called guard:81dfbb7b2bb8037b
  receipt bce9fdaf50a7-0000 written to .mint/guard.json — the log now holds 1

Status 2. Held: the command changes something and nobody has agreed to it. Nothing was run, and the decision is in the log before it was made.

3. A person approves that exact action

mint approve --action guard:81dfbb7b2bb8037b --days 1 --note "I read the diff"0
  for the runtime whose key is /tmp/start-demo-home/.secrets/mint-receipt.key: bce9fdaf50a7
  approved «guard:81dfbb7b2bb8037b»
  by 11b16d62878b (/root/.secrets/mint-approver.key), valid 1 day(s)
  written to /tmp/start-demo/approval.json
  the runtime has to pin this key to accept it:
    MINT_APPROVERS=<a file listing 11b16d62878b> MINT_APPROVAL_FILES=/tmp/start-demo/approval.json

The approval names the action, so it cannot authorise a different one, and it is signed, so the receipt can name who gave it.

4. Present it

mint guard --command "git commit -m 'first change'" --approval approval.json --receipts .mint0
  approvers pinned from /tmp/start-demo/approvers.json: dmitry (11b16d62878b)
  note: this approval was not issued from a terminal — a script, a job, or an agent ran the command. It is recorded as such in the receipt.
  write   allow  — an approval bound to this exact action was presented
  decided by mint.policy/0.1 v1, rules a8bed408510ec43a
  the action is called guard:81dfbb7b2bb8037b
  approved by dmitry, /tmp/start-demo/approval.json
  receipt bce9fdaf50a7-0001 written to .mint/guard.json — the log now holds 2

Status 0. Allowed, with the approver's name in the receipt. The note about the terminal is honest and worth reading: this page issues the approval from a script, so the record says so. When you do it, it will say `terminal` instead.

5. Present the same approval again

mint guard --command "git commit -m 'first change'" --approval approval.json --receipts .mint1
  approvers pinned from /tmp/start-demo/approvers.json: dmitry (11b16d62878b)
  note: this approval was not issued from a terminal — a script, a job, or an agent ran the command. It is recorded as such in the receipt.
  write   refuse — this action was already released once, as receipt bce9fdaf50a7-0001; a repeat is not performed
  decided by mint.policy/0.1 v1, rules a8bed408510ec43a
  the action is called guard:81dfbb7b2bb8037b
  approved by dmitry, /tmp/start-demo/approval.json
  receipt bce9fdaf50a7-0002 written to .mint/guard.json — the log now holds 3

Status 1. The approval was spent when the action was performed, and the refusal comes from the log rather than from memory — it survives restarts, days and machines, and it names the receipt that released it.

3 decisions — one held, one allowed, one refused — every signature and every link in the chain checked, and every decision re-derived from the published rules. The log is the whole record: no separate audit trail to reconcile, no server to ask.

7. Put it in front of your agent

echo '<the harness payload>' | mint hook0
permissionDecision: deny
reason: mint held this command before it ran: this step commits something and no approval bound to it was presented
Nothing was executed. A person approves this exact action with:
mint approve --action guard:f724133e1ef68470 --days 1 --note "why" --out approval.json
and the next attempt proceeds. Do not look for another way to run it.

This is how the agent is stopped: hooks/hooks.json registers a PreToolUse hook, the harness runs it before every shell command and obeys the answer. The skill explains; this enforces. Measured rather than assumed — a live session with only the skill installed committed without asking and the log stayed empty. With the hook, the same session was blocked, said so, and printed the command that approves the action. Both Claude Code and Codex read this same file; Codex asks you to trust the hook once before it will run it, and until you do, the gate is not in the path there.

What it will not do

It will not tell you whether an action is safe — only who agreed to it, and that they did. It will not let a held action through without a person: there is no flag that means "just this once", and a refusal is not overridable by configuration. An approval cannot be delegated to another runtime (it can be withdrawn, by somebody the runtime pins, and nobody else). And the published example cannot show a real counterparty, because both keys are on one machine — the mechanism is shown, the trust is yours to create.

The log is at .mint/guard.json. Read it with mint receipts, and check somebody else's with the same command — the verifier is the same binary, and it needs nothing from us.
