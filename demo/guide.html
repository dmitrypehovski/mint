An agent does a task once by asking a model. Then it never asks again.

mint learns a task the first time — a model decides every step — and writes down what it decided. From then on the task runs the same way, with no model involved, and every step leaves a signed receipt before it happens.

1 · the problem

You cannot tell what an agent did. And it will not do it the same way twice.

Agents now press buttons, fill forms, tidy files, move money. When one has finished, what do you have? A log the agent wrote about itself, if it kept one. A page that looks right, if you were watching. Nothing a second person could check tomorrow.

It gets worse with repetition. Ask a model to do the same fifty steps on Tuesday that it did on Monday, and it may take a different route, skip a step, or decide halfway through that the job is done. The work is real, and so is the doubt about it.

That doubt is the whole problem. It is why agent work is hard to approve, hard to hand to somebody else, and hard to charge for.

2 · what it is

A runtime that decides once with a model, and then does without it.

Point mint at a screen or a folder and give it a goal in plain words. The first run is an ordinary agent: a model looks at what is there and chooses each step. But mint writes down every decision before it acts, and what it writes down is a program, not a recording — "the pull requests tab, then the first pull request, then its commits" keeps working when the page has different contents.

Afterwards the same task runs from that program: the same steps, in the same order, with no model in the loop, and a signed receipt for each step before it happens.

Two things follow, and they are the whole product. The hundredth run does what the first run did — so somebody can approve it once and leave it alone. And there is a record that says what happened, step by step, that a person who was not there can check.

3 · who it is for

Three people, for three different reasons.

The person who has to approve it

You are the one who says yes when an agent touches something real. mint gives you the exact action to approve — this move, in this folder — instead of "the agent". An approval for step three cannot authorise step four.

The team that runs it every day

Same task, fifty times a week. The model is asked once, and the fifty-odd decisions it used to make come back as zero. What changes is not only the bill: the same input gives the same output, tomorrow too.

Whoever has to check it later

An auditor, a client, the next person in the job. They get a chain of signed receipts they can verify themselves, in software they can read, with the rules the work was done under attached to it.

If none of those is you, this is probably not for you yet — and that is a fair thing to know in three paragraphs rather than after reading the whole site.

4 · how it works

Four steps, and one of them is the point.

  1. Learn. A model decides each step once: what to click, what to type, which file to move. Every decision is written down with the words by which the target is recognised next time.
  2. Decide before acting. Before anything happens, the step goes past a gate that answers one question: does this only look, or does it change something? Looking passes. Changing waits for an approval. Anything that cannot be described at all is refused rather than tried.
  3. Replay without a model. The task runs from the written-down steps. No model, no questions, no drift — and each step is checked to see that it produced what it was meant to.
  4. Leave a receipt. Each step is signed before it happens, chained to the step before it, and tied to the rules document the run was made under. Edit any of it and the check fails at the exact receipt.

6 · the record

The receipt is the product. The speed is what makes it usable.

Speed matters because it is what makes approving possible: nobody reviews a run that takes ten minutes and answers differently each time, but fifty lines that will be the same tomorrow can be read and approved. What you keep, though, is the record — and it is built to survive people, not to flatter the agent.

  • Signed before the action, so a step that never happened cannot appear in the log.
  • Chained, so removing or reordering one receipt is detectable — and the check says which.
  • Bound to the rules document, so a change in the rules invalidates what was done under the old ones.
  • Topped by a checkpoint: the runtime signs the head of its own log — how many receipts, which one it ends with — and a second key countersigns exactly that head. A log that is later presented with receipts missing is caught by the witness's own record of what it saw, and the countersignature dates that head without asking the runtime what time it is.
  • Written to say what it does not prove: anything about the world, and nothing about a witness that watches a log recording a lie.

7 · what it does not do

The edges, stated here rather than found later.

  • It is not faster than a script. For a task you can already script, write the script. mint is for the task where you cannot, because deciding which thing to do next needs judgement — and the judgement is what you want written down and approved once.
  • Pages at one depth can look like the same page to it. Two path segments are read as a site's project root, which is what lets a skill learned on one repository run on another; the cost is that an address like /fieldwork/submit has no name of its own, and a run that ends there is pinned by its last segment rather than by its shape.
  • The witness on this site is on the same machine. The log's head is signed by the runtime and countersigned by a second key, and a log that shrank since the last sighting is caught by name rather than argued about — but here both keys live on one computer, so what you see is the mechanism working, not a reason to trust it. A real witness is somebody who does not hold the log. And a witness says nothing about the world: it countersigns what was recorded, including a lie, and it can only say that the record did not change afterwards.
  • Transfer is proven on one family so far. A skill learned on one repository runs on another; the same claim on other kinds of site is not yet shown.
  • The check that decides success is a model, and it is wrong sometimes. It failed correct work three times by being shown a truncated view. It now lists what is in the wrong place instead of answering yes or no — and the work is verified with a script anyway.

8 · take it

Clone it, build it, and check the published record yourself.

It is open source and it does not depend on us: a Rust binary, a rules file, a key file. Every number on this site came out of a run, and the runs are reproducible from the repository.

git clone https://github.com/dmitrypehovski/mint && cd mint
cargo build --release
./target/release/mint probe --url https://example.com      # what it hands to a model
./target/release/mint demo  --skill gh-pr-chain.skill.json \
    --start https://github.com/rust-lang/rust --receipts out.json

The published receipts, the rules document and the second signature are served from this site, and the verifier checks them in front of you: receipts.json · policy.json · endorsement.json

9 · where it sits

A trade needs a receipt for the work, and that line is missing.

Agent work is traded on three lines today: who the agent is, what it costs to run, and what it claims. The line where the work actually happens — what it did, in what order, under which rules — is not in the market. mint is that line: something an agent can carry, and something a buyer can check without trusting either side.

It is built for the ARLI ecosystem and works anywhere: nothing here needs our permission, and most of it does not need our code.
