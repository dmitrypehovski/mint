invoice-2026-03-0147.pdf belongs in 2026-03. Nothing else is stated; the rule is in the names. A model decides each of the fifty files once, and mint writes each decision down as a step. Afterwards the fifty steps run without a model at all.

What the receipt leaves behind: fifty signed records, one per file, each written before the command ran, saying which file moved where and under which rules. Checking the work afterwards is not an argument about what happened — it is reading fifty lines.

Checked independently of the runtime: a script walked the finished directory and found nothing left loose and nothing in the wrong folder, in the run that was learned and in a second directory it had never seen.

This is the plainest possible work: type in a field, type in another, tick a box, choose a radio, press send. It is also the task a runtime that only counts navigation can never learn, because the address does not change until the very last step.

Learning needs the writes to happen once; replaying should not be trusted with them by default. So learning happens under a document that says which writes are permitted, and the replay goes back to the strict document — where the same skill stops at the first move and names the exact action that needs approving.

What this gives you: an approval that is bound to one specific action, not to "the agent". An approval for step three cannot authorise step four, which is the substitution a page can attempt between the moment a person agrees and the moment the action runs.

Every receipt is signed before the action, chained to the one before it, and bound to the rules document the run was made under. Edit any of it and the check fails at the exact receipt — which is the difference between a log and a record.

And what it does not claim: whose clock signed it is the signer's clock; the environment the observations came from is not witnessed by anybody else; the runtime carries a counter-signature slot and never fills it. Those are the holes, written down as holes.

The saving is exactly what the first run cost, paid once instead of every time. There is no second trick: the fifty decisions cost fifty questions now and none afterwards, and the numbers on the comparison pages are those two numbers.

In money this is small. Fifty decisions on a cheap model costs about a cent and a half, so nobody buys this to save a cent. What is being bought is that the hundredth run does the same thing as the first, and that somebody can read what was done without having watched it.

what did not work

Three things that are not on the demonstration pages, and why.

A fifty-field web form. The same model that handles fifty files in a directory loses its place on one long page: it filled thirty-five of fifty fields and then pressed Send, twice, on separate attempts. The skill exists and is honestly marked unverified, and it stays off the demonstration pages until it works. Directory work of the same length is fine, because there each step removes the thing it acted on — the page does not.

Following a CI workflow's runs. Two hops in, the model cannot find the link to the run in the list, and the workflow list loads later than the runtime looks at it. Unverified, not shown.

The judge that decides whether a run succeeded. It failed correct work three times, with confident reasons, because it was shown a truncated view of the finished state — it named a file as misplaced that was in the right folder. It is now shown the whole state and required to name a concrete item if it says the work is not done, and the work is checked with a script anyway. Those three failures are worth more to a reader than a page that only shows things working.
